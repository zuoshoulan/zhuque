## 开始使用

本规范包含了对 RTB（实时竞价）接口的详细说明。并非所有对象都是必需的，每个对象可能包含多个可选参数。为了帮助首次阅读本规范的读者，我们指出了支持各种场景（横幅、视频等）的最小可行实时竞价接口所需的基本字段。

最小可行接口应包括必需和推荐参数，但这些参数的范围可能仅限于特定场景。在这些情况下，描述列可能会进一步限定其必需或推荐状态。可选参数可以包括在内，以确保各方获得最大价值。

**重要提示：**由于推荐参数不是必需的，它们可能无法从所有供应源获得。建议 OpenRTB 交易的所有各方制定集成清单，以确定供应方在竞价请求中支持哪些属性，以及需求方需要哪些属性进行广告决策。

## 1. 介绍

### 1.1 使命/概述

OpenRTB 项目的使命是通过为广告买家和发布商库存卖家之间的通信提供开放的行业标准，促进实时竞价（RTB）市场的增长。这些标准包括但不限于实际的实时竞价协议、信息分类法、离线配置同步等。

本文档规定了实时竞价接口的标准，该标准源于之前 OpenRTB 在"阻止列表项目"和"OpenRTB 移动"项目上的合作。这些协议标准旨在简化发布商库存供应商（即交易所、与发布商合作的网络和卖方平台）与该库存的竞争买家（即出价方、需求方平台或与广告主合作的网络）之间的连接。

OpenRTB 的总体目标一直是创建买家和卖家之间通信的通用语言。目的不是精确规定每个企业如何运营。作为一个项目，我们的目标是使各方之间的集成更容易，以便创新可以在生态系统中的每个企业更深层面上发生。

### 1.2 OpenRTB 历史

OpenRTB 于 2010 年 11 月作为三个需求方平台（DataXu、MediaMath 和 Turn）与三个卖方平台（Admeld、PubMatic 和 The Rubicon Project）之间的试点项目启动。第一个目标是标准化各方之间交换阻止列表的通信。OpenRTB 阻止列表规范 1.0 版于 2010 年 12 月发布。

在行业积极响应后，Nexage 向 OpenRTB 项目提出了一项建议，创建一个专注于实际实时竞价请求/响应协议并专门支持移动广告的 OpenRTB API 规范。移动子委员会在代表买方公司（DataXu、Fiksu 和 [X+1]）和代表卖方公司（Nexage、Pubmatic、Smaato 和 Jumptap）之间成立。该项目产生了 OpenRTB Mobile 1.0 规范，于 2011 年 2 月发布。

在移动规范发布后，视频子委员会成立，视频广告交易所（BrightRoll 和 Adap.tv）与 DataXu 和 ContextWeb 合作纳入视频支持。目标是在一个文档中纳入对展示、视频和移动的支持。这项工作产生了 OpenRTB 2.0，于 2011 年 6 月作为统一标准发布。

由于行业的广泛采用，OpenRTB 于 2012 年 1 月随 2.1 版本的发布被采纳为 IAB 标准。规范技术内容的治理仍由 OpenRTB 社区及其治理规则负责。

### 1.5 术语

| 术语 | 定义 |
|------|------|
| **RTB** | 实时竞价单个展示（即在消费者等待时） |
| **Exchange（交易所）** | 在每个展示的出价方之间进行拍卖的服务 |
| **Bidder（出价方）** | 在实时拍卖中竞争获取展示的实体 |
| **Seat（席位）** | 希望获得展示并使用出价方代表其行事的广告实体（例如，广告主、代理商）；出价方的客户，通常是广告预算的所有者 |
| **Publisher（发布商）** | 运营一个或多个站点的实体 |
| **Site（站点）** | 广告支持的内容，包括 Web 和应用程序，除非另有说明 |
| **Deal（交易）** | 发布商和席位之间根据某些条款购买展示的预先安排的协议 |

## 2. OpenRTB 基础

下图说明了交易所与其出价方之间的 OpenRTB 交互。广告请求来自发布商站点或应用程序。对于每个入站广告请求，竞价请求会广播给出价方，根据现行拍卖规则评估响应，并选择获胜者。获胜的出价方通过获胜通知收到拍卖获胜的通知。广告标记既可以前瞻性地包含在竞价中，也可以作为对获胜通知的响应。还可以提供单独的计费通知，以适应交易所制定的不同策略，这些策略超出了 OpenRTB 规范的范围（例如，基于设备交付、可视性的计费等）。获胜通知通知出价方的定价算法已成功，而计费通知指示应实际应用支出。失败通知也可用于通知出价方其竞价未获胜的原因。

获胜、计费和失败通知的 URL 以及广告标记本身可以包含多个标准宏中的任何一个，使交易所能够向出价方传达关键数据（例如，结算价格）。

本规范重点关注竞价请求和响应以及获胜、计费和失败通知的实时交互。其他交互（例如，阻止列表同步、流量控制、创意审核等）是未来 OpenRTB 计划或替代项目的候选者。

### 2.1 传输

交易所和其出价方之间的基础协议是 HTTP。具体而言，HTTP POST 是竞价请求所必需的，以容纳比 HTTP GET 更大的有效负载并促进二进制表示的使用。获胜通知可根据交易所的决定使用 POST 或 GET。

返回内容的调用（例如，任何竞价响应、返回标记的获胜通知）应返回 HTTP 代码 200。对有效请求不返回内容的调用（例如，空的竞价响应，这是表示不竞价的一种选择，不返回标记的获胜通知）应返回 HTTP 204。无效调用（例如，包含格式错误或损坏的有效负载的竞价请求）应返回 HTTP 400 且不包含内容。

**最佳实践**：改进连接性能的最简单和最有效的方法之一是启用 HTTP 持久连接，也称为 Keep-Alive。这通过减少连接管理开销以及接口双方的 CPU 利用率，对整体性能产生深远影响。

### 2.2 安全性

HTTPS（即安全 HTTP）不是 OpenRTB 合规所必需的。然而，行业中使用 HTTPS 来增强交易所/出价方通信安全性的趋势正在增长。因此，建议交易所和出价方考虑同时支持 HTTP 和 HTTPS。

### 2.3 数据格式

JSON（JavaScript 对象表示法）是竞价请求和竞价响应数据有效负载的建议格式。选择 JSON 是因为其人类可读性和紧凑性的结合。数据有效负载在第 3 节和第 4 节中描述。

可选地，交易所也可以提供二进制表示（例如，压缩的 JSON、ProtoBuf、Avro 等），这些在传输时间和带宽方面可能更有效。IAB 技术实验室可能会为这些或其他格式提供参考实现。如果可用，强烈建议使用这些 IAB 参考实现以减少特定于交易所的变化。

竞价请求使用 Content-Type HTTP 头将表示指定为 MIME 类型。标准 JSON 表示的 MIME 类型是"application/json"，如图所示。竞价响应的格式必须与竞价请求相同。

```
Content-Type: application/json
```

如果使用替代的二进制表示，交易所或 SSP 应适当指定 Content-Type。例如："Content-Type: avro/binary"或"Content-Type: application/x-protobuf"。如果缺少内容类型，出价方应假设类型是 application/json，除非交易所选择了不同的默认值。

按照惯例，属性的缺失具有正式含义。在大多数情况下，这表示值未知，除非另有说明。

### 2.4 数据编码

压缩交易所和出价方之间发送的数据非常有益。压缩大大减少了传输的数据大小，从而为交易所和出价方节省了网络带宽。为了充分实现这种节省，应该对交易所发送的竞价请求和出价方返回的竞价响应都启用压缩。

可以使用标准 HTTP 1.1 机制在竞价响应上启用压缩。大多数 Web 服务器已经支持响应内容的 gzip 压缩，因此它是一个理想的选择。为了向交易所发出他们希望压缩响应的信号，应该设置标准 HTTP 1.1 Accept-Encoding 头。使用的编码值应该是"gzip"。

```
Accept-Encoding: gzip
```

此头向出价方表示交易所能够接受响应的 gzip 编码。如果出价方服务器支持此功能并正确配置，它将自动响应 gzip 编码的内容。这将使用标准 HTTP 1.1 Content-Encoding 头指示。

```
Content-Encoding: gzip
```

要在竞价请求上启用压缩，必须事先在交易所和出价方之间达成支持此功能的协议。这类似于使用自定义数据格式时的情况，因为交易所在发送竞价请求之前必须知道格式和编码。如果出价方支持，交易所应该通过设置 HTTP 1.1 Content-Encoding 头指示它正在发送 gzip 压缩的竞价请求。使用的编码值应该是"gzip"。

```
Content-Encoding: gzip
```

如果未设置此头，则假设请求内容未编码。在 HTTP 1.1 中，Content-Encoding 头通常仅用于响应内容。然而，通过在请求内容中也使用此头，我们能够指示请求被压缩，无论使用的数据格式如何。这是有用的，因为即使是二进制数据格式也可以受益于压缩。

### 2.5 OpenRTB 版本 HTTP 头

OpenRTB 版本应该使用自定义头参数在竞价请求的头中传递。这将允许出价方在尝试解析请求之前识别包含的消息的版本。

此外，建议（虽然可选）出价方在响应的 HTTP 头中放置格式相同的消息，其中包含出价方已实现的协议版本。消息可能包含与请求头不同的版本号。

```
x-openrtb-version: 2.5
```

此版本应指定为 <major>.<minor>（例如，2.5）。版本的第一个或第二个级别增量是协议的更改。通常，第二级更改应该向后兼容，而第一级更改不需要向后兼容。任何第三级修订（如 2.5.1）不应更改协议本身；仅更改不影响协议内容的描述和说明。第三级版本不应包含在此头中，因为它们不应具有技术影响。

### 2.6 隐私设计

OpenRTB 项目完全支持广告买家和卖家指定的隐私政策。特别是 OpenRTB 支持不跟踪（第 3.2.18 节）、COPPA 限制信号（第 7.5 节），以及通过 User 对象（第 3.2.20 节）将用户偏好从卖家传递给买家的能力。

### 2.7 与库存质量指南的关系

OpenRTB 完全符合库存质量指南（IQG），网址为：www.tagtoday.net/iqg。特别是，本规范中使用的许多分类法和列表源自 IQG 或 IAB 技术实验室。

### 2.8 自定义和扩展

OpenRTB 规范允许特定于交易所的自定义和规范扩展。任何对象都可能包含扩展。为了保持扩展字段在平台间的一致性，它们应一致地命名为"ext"。

## 3. 竞价请求规范

当交易所或其他供应源向出价方发送竞价请求时，RTB 交易开始。竞价请求由顶级竞价请求对象、至少一个展示对象组成，还可以选择包含提供展示上下文的附加对象。

### 3.1 对象模型

以下是竞价请求的对象模型。顶级对象（即在 JSON 中为未命名的最外层对象）在模型中表示为 BidRequest。在其直接子对象中，只有 Imp 在技术上是必需的，因为它对于描述正在出售的展示是基本的，并且至少需要 Banner（可能允许多个格式）、Video、Audio 和 Native 之一来定义展示类型（即发布商愿意接受的一种或多种；尽管竞价将恰好针对这些指定类型中的一种）。展示可以选择性地受私有市场约束。

BidRequest 的其他子对象为出价方做出定向和定价决策提供各种形式的信息。这包括有关用户、他们使用的设备、其中任何一个的位置、监管约束以及展示发生的内容和媒体的详细信息。在后者上，站点（即网站）和应用程序（即通常在移动设备中的非浏览器应用程序）之间存在区别。称为 DistributionChannel 的抽象类只是一个建模概念，用于指示 BidRequest 与站点或应用程序相关，但不能同时相关（即分发渠道是站点和应用程序的抽象）。站点和应用程序都可以通过有关其发布商、内容和内容制作者的数据进一步描述。

模型图中未显示的是扩展对象。这是一个结构未定义的对象，可以添加到任何其他对象以传达特定于交易所的标准扩展。使用这些对象的交易所负责向其出价方发布其扩展。

下表总结了竞价请求模型中的对象，并作为后续小节中详细定义的索引。

| 对象 | 章节 | 描述 |
|------|------|------|
| **BidRequest** | 3.2.1 | 顶级对象 |
| **Source** | 3.2.2 | 关于拍卖后决策的请求源详细信息（例如，头部竞价） |
| **Regs** | 3.2.3 | 适用于此竞价请求中所有展示的监管条件 |
| **Imp** | 3.2.4 | 特定展示描述的容器；每个请求至少 1 个 |
| **Metric** | 3.2.5 | 关于展示的可量化通常是历史数据点 |
| **Banner** | 3.2.6 | 横幅展示（包括横幅内视频）或视频伴随广告的详细信息 |
| **Video** | 3.2.7 | 视频展示的详细信息 |
| **Audio** | 3.2.8 | 音频展示的容器 |
| **Native** | 3.2.9 | 符合动态原生广告 API 的原生展示容器 |
| **Format** | 3.2.10 | 横幅的允许尺寸 |
| **Pmp** | 3.2.11 | 适用于此展示的私有市场（PMP）交易集合 |
| **Deal** | 3.2.12 | 卖家和买方之间关于此展示的交易条款 |
| **Site** | 3.2.13 | 调用展示的网站的详细信息 |
| **App** | 3.2.14 | 调用展示的应用程序的详细信息 |
| **Publisher** | 3.2.15 | 控制站点或应用程序的内容并分发其实体的实体 |
| **Content** | 3.2.16 | 关于已发布内容本身的详细信息，其中将显示广告 |
| **Producer** | 3.2.17 | 内容的制作者；不一定是发布商（例如，联合供稿） |
| **Device** | 3.2.18 | 显示内容和展示的设备的详细信息 |
| **Geo** | 3.2.19 | 设备或用户家庭基地的位置，取决于父对象 |
| **User** | 3.2.20 | 设备的人类用户；广告受众 |
| **Data** | 3.2.21 | 来自特定数据源的附加用户定向数据集合 |
| **Segment** | 3.2.22 | 来自特定数据源的关于用户的具体数据点 |

### 3.2 对象规范

以下小节定义了竞价请求模型中的每个对象。整个过程中使用了几个约定：

- 属性在其遗漏会在技术上破坏协议时是"必需的"
- 一些可选属性由于其较高的业务重要性而被标记为"推荐的"
- 除非明确指定默认值，否则省略的属性被解释为"未知"

#### 3.2.1 对象：BidRequest

顶级竞价请求对象包含全局唯一的竞价请求或拍卖 ID。此 id 属性是必需的，至少一个展示对象（第 3.2.4 节）也是如此。此顶级对象中的其他属性建立适用于所提供所有展示的规则和限制。

还有几个子对象为潜在买家提供详细数据。其中包括 Site 和 App 对象，它们描述展示出现的发布媒体类型。这些对象是高度推荐的，但只有一个适用于给定的竞价请求，具体取决于媒体分别是基于浏览器的 Web 内容还是非浏览器应用程序。

**属性说明：**

| 属性 | 类型 | 描述 |
|------|------|------|
| **id** | string; required | 交易所提供的竞价请求的唯一 ID |
| **imp** | object array; required | 表示所提供展示的 Imp 对象（第 3.2.4 节）数组。至少需要 1 个 Imp 对象 |
| **site** | object; recommended | 通过站点对象（第 3.2.13 节）有关发布商网站的详细信息。仅适用于并推荐用于网站 |
| **app** | object; recommended | 通过 App 对象（第 3.2.14 节）有关发布商应用程序（即非浏览器应用程序）的详细信息。仅适用于并推荐用于应用程序 |
| **device** | object; recommended | 通过设备对象（第 3.2.18 节）有关将向其交付展示的用户设备的详细信息 |
| **user** | object; recommended | 通过用户对象（第 3.2.20 节）有关设备人类用户的详细信息；广告受众 |
| **test** | integer; default 0 | 测试模式指示器，其中拍卖不可计费，0 = 实时模式，1 = 测试模式 |
| **at** | integer; default 2 | 拍卖类型，1 = 第一价格，2 = 第二价格加。可以使用大于 500 的值定义特定于交易所的拍卖类型 |

| **allimps** | integer; default 0 | 指示交易所是否可以验证所提供的展示代表上下文中可用的所有展示（例如，网页上的所有展示，所有视频点，如前贴片/中贴片/后贴片）以支持路障的标志。0 = 否或未知，1 = 是，所提供的展示代表所有可用的展示 |
| **cur** | string array | 使用 ISO-4217 字母代码的竞价请求允许的货币数组。仅当交易所接受多种货币时才推荐 |
| **wlang** | string array | 使用 ISO-639-1-alpha-2 的创意白名单语言。省略意味着没有具体限制，但如果可用，建议买家考虑设备和/或内容对象中的语言属性 |
| **bcat** | string array | 使用 IAB 内容类别的阻止广告主类别。参考列表 5.1 |
| **badv** | string array | 通过其域（例如，"ford.com"）阻止的广告主阻止列表 |
| **bapp** | string array | 通过其平台特定于交易所独立应用程序标识符阻止的应用程序阻止列表。在 Android 上，这些应该是捆绑包或包名称（例如，com.foo.mygame）。在 iOS 上，这些是数字 ID |

| **regs** | object | 一个 Regs 对象（第 3.2.3 节），指定适用于此请求的任何行业、法律或政府法规 |
| **ext** | object | 特定于交易所的 OpenRTB 扩展的占位符 |

#### 3.2.2 对象：Source

此对象描述交易所上游竞价请求源的实体的性质和行为。此对象的主要目的是定义交易所本身不控制最终决策时的拍卖后或上游决策。这种情况的一个常见示例是头部竞价，但它也可以适用于上游服务器实体，例如另一个 RTB 交易所、中介平台，或在决策中结合直接活动与第三方需求的广告服务器。

**属性说明：**

| 属性 | 类型 | 描述 |

| **pchain** | string; recommended | 包含 TAG 支付 ID 协议 v1.0 中描述的嵌入语法的支付 ID 链字符串 |

#### 3.2.3 对象：Regs

此对象包含适用于请求的任何法律、政府或行业法规。coppa 标志指示请求是否受美国联邦贸易委员会的美国儿童在线隐私保护法（"COPPA"）法规的约束。

**属性说明：**

| 属性 | 类型 | 描述 |
|------|------|------|
| **coppa** | integer | 指示此请求是否受美国 FTC 建立的 COPPA 法规约束的标志，0 = 否，1 = 是。参考第 7.5 节以获取更多信息 |
| **ext** | object | 特定于交易所的 OpenRTB 扩展的占位符 |

#### 3.2.4 对象：Imp

此对象描述正在拍卖的广告位或展示。单个竞价请求可以包含多个 Imp 对象，其用例可能是支持在给定页面上销售所有广告位置的交易所。每个 Imp 对象都有一个必需的 ID，以便竞价可以单独引用它们。

Banner（第 3.2.6 节）、Video（第 3.2.7 节）和/或 Native（第 3.2.9 节）对象作为 Imp 对象的子对象的存在表示所提供的展示类型。发布商可以选择一种类型，这是典型情况，或自行混合它们。但是，对此展示的任何给定竞价必须符合提供的类型之一。

**属性说明：**

| 属性 | 类型 | 描述 |
|------|------|------|
| **id** | string; required | 在竞价请求上下文中此展示的唯一标识符（通常，从 1 开始并递增） |
| **metric** | object array | 度量对象（第 3.2.5 节）数组 |
| **banner** | object | 横幅对象（第 3.2.6 节）；如果此展示作为横幅广告机会提供则是必需的 |
| **video** | object | 视频对象（第 3.2.7 节）；如果此展示作为视频广告机会提供则是必需的 |
| **audio** | object | 音频对象（第 3.2.8 节）；如果此展示作为音频广告机会提供则是必需的 |
| **native** | object | 原生对象（第 3.2.9 节）；如果此展示作为原生广告机会提供则是必需的 |
| **pmp** | object | 包含适用于此展示的任何私有市场交易的 Pmp 对象（第 3.2.11 节） |
| **displaymanager** | string | 负责渲染广告的广告中介合作伙伴、SDK 技术或播放器的名称（通常是视频或移动设备）。一些广告服务器使用它来按合作伙伴自定义广告代码。推荐用于视频和/或应用程序 |
| **displaymanagerver** | string | 负责渲染广告的广告中介合作伙伴、SDK 技术或播放器的版本（通常是视频或移动设备）。一些广告服务器使用它来按合作伙伴自定义广告代码。推荐用于视频和/或应用程序 |
| **instl** | integer; default 0 | 1 = 广告是插页或全屏，0 = 非插页 |
| **tagid** | string | 用于启动拍卖的特定广告位或广告标签的标识符。这对于调试任何问题或买家优化可能很有用 |
| **bidfloor** | float; default 0 | 以 CPM 表示的此展示的最低竞价 |
| **bidfloorcur** | string; default "USD" | 使用 ISO-4217 字母代码指定的货币。如果交易所允许，这可能与出价方返回的竞价货币不同 |
| **clickbrowser** | integer | 指示在应用程序中点击创意时打开的浏览器类型，0 = 嵌入式，1 = 原生。请注意，iOS 9.x 设备上的 Safari 视图控制器对于此属性被视为原生浏览器 |
| **secure** | integer | 指示展示是否需要安全 HTTPS URL 创意资源和标记的标志，0 = 非安全，1 = 安全。如果省略，安全状态未知，但可以假设支持非安全 HTTP |
| **iframebuster** | string array | 支持的 iframe 破坏者的特定于交易所的名称数组 |
| **exp** | integer | 关于拍卖和实际展示之间可能经过的秒数的建议 |
| **ext** | object | 特定于交易所的 OpenRTB 扩展的占位符 |

#### 3.2.5 对象：Metric

此对象作为度量数组与展示关联。这些度量可以提供对展示的洞察以协助决策，例如最近平均可视性、点击率等。每个度量都由其类型标识，报告度量的值，并可选地标识测量值的源或供应商。

#### 3.2.6 对象：Banner

Banner 作为 Imp 对象的子对象的存在表示此展示作为横幅类型展示提供。在发布商自行决定的情况下，同一展示也可以作为视频、音频和/或原生提供，方法是将这些类型的对象也作为 Imp 子对象包括在内。但是，对此展示的任何给定竞价必须符合提供的类型之一。

| **expdir** | integer array | 展开方向（参考第 5.5 节） |
| **api** | integer array | API 框架（参考第 5.6 节） |
| **id** | string | 交换特定的唯一标识符，用于在竞价响应中引用特定横幅元素 |
| **vcm** | integer | 视频创意模块数；如果未指定，则假设无限制 |
| **ext** | object | 特定于交易所的 OpenRTB 扩展的占位符 |

## 4. 竞价响应规范

在竞价响应中，出价方返回其竞价以及标识它们所竞价的展示的信息。竞价响应必须至少包含一个竞价对象才能被视为有效的竞价。

### 4.1 对象模型

以下是竞价响应的对象模型。顶级对象（即在 JSON 中为未命名的最外层对象）在模型中表示为 BidResponse。Seatbid 对象数组包含实际竞价。每个竞价都通过其 impid 属性映射到竞价请求中的特定展示。

### 4.3 广告投放选项

#### 4.3.1 在获胜通知上投放的标记

在此方法中，出价方在获胜通知 URL（nurl）中返回广告标记。当交易所向出价方发送获胜通知时，出价方在响应中返回广告标记。

**优点：**
- 如果没有获胜，则不下载广告资源
- 竞价响应小，延迟低
- 允许在获胜时进行创意优化

**缺点：**
- 需要额外的服务器往返来获取广告
- 在高延迟情况下可能导致广告投放失败

#### 4.3.2 在竞价中投放的标记

在此方法中，出价方在竞价响应中直接返回广告标记（使用 adm 属性）。交易所立即缓存此标记，并在获胜时投放它。

**优点：**
- 最小化广告投放延迟
- 无需额外的服务器往返

**缺点：**
- 即使没有获胜，也会下载广告资源
- 竞价响应更大，延迟更高
- 获胜时无法进行创意优化

#### 4.3.3 广告投放方法的比较

| 因素 | 获胜通知上投放 | 竞价中投放 |
|------|----------------|-------------|
| 延迟 | 较高 | 较低 |
| 竞价响应大小 | 较小 | 较大 |
| 带宽使用 | 较低 | 较高 |
| 创意优化 | 是 | 否 |

### 4.4 替换宏

交易所可以在获胜通知、计费通知和失败通知的 URL 以及广告标记本身中使用标准宏。这些宏使交易所能够向出价方传达关键数据。

| 宏 | 描述 |
|----|------|
| `${AUCTION_PRICE}` | 结算价格（以微美元为单位） |
| `${AUCTION_ID}` | 竞价请求/拍卖 ID |
| `${AUCTION_IMP_ID}` | 展示 ID |
| `${AUCTION_SEAT_ID}` | 席位 ID |
| `${AUCTION_BID_ID}` | 竞价 ID |
| `${AUCTION_AD_ID}` | 广告 ID |
| `${AUCTION_CURRENCY}` | 货币 |
| `${AUCTION_LOSS}` | 失败原因（仅适用于失败通知） |

## 7. 实施注意事项

### 7.1 不竞价信号

出价方可以通过以下方式表示不竞价：

1. 返回空的竞价响应（HTTP 204）
2. 返回包含 nbr 属性的 BidResponse 对象
3. 返回空的 seatbid 数组

### 7.2 展示过期

展示具有有限的寿命。出价方应遵守交易所设置的 tmax 值，并在超时前返回竞价。

### 7.3 PMP 和直接交易

私有市场（PMP）允许发布商与特定买方进行直接交易。直接交易具有预定义的条款和条件。

交易可以是：
- **第一价格**：获胜者支付其竞价价格
- **第二价格加**：获胜者支付第二高价加一个小增量

### 7.4 可跳过性

某些视频广告允许用户跳过广告。交易所应通过 skip、skipmin 和 skipafter 属性传达此信息。

### 7.5 COPPA 法规标志

COPPA（儿童在线隐私保护法）法规适用于针对儿童的网站和服务。当 coppa 标志设置为 1 时，出价方必须确保其竞价符合 COPPA 要求。
