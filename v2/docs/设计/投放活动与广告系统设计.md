# 投放活动与广告系统设计文档

## 1. 概述

本系统采用**两层架构**设计投放活动和广告，符合OpenRTB DSP系统的业界实践。

### 1.1 架构层级

```
Campaign (投放活动)
  ↓ 1:N
Ad (广告)
  ↓ N:1
Creative (创意)
  ↓ 1:N
Material (素材)
```

### 1.2 层级职责

| 层级 | 职责 | 核心字段 |
|------|------|----------|
| Campaign | 钱包 | 预算、时间、状态 |
| Ad | 策略 | 出价、定向、创意关联 |
| Creative | 内容 | 落地页、展示URL |
| Material | 文件 | 图片、视频等素材 |

### 1.3 为什么两层？

**业界实践**：
- Beeswax、RTB4FREE等开源DSP均为两层
- Google/Facebook广告平台用三层，但那是搜索/社交广告，不是DSP

**DSP特点**：
- 实时竞价要求毫秒级响应
- Ad是完整竞价单元
- 减少层级 = 提升查询效率

**为什么必须记录每次竞价？**
1. **对账**：广告主核对花费
2. **排查**：为什么没展示？为什么输了？
3. **分析**：赢率、响应时间、效果分析
4. **合规**：审计要求

**数据保留**：
- 定期删除90天前的数据：`DELETE FROM rtb_bid_log WHERE request_time < DATE_SUB(NOW(), INTERVAL 90 DAY)`
- 后期数据量大了再加分区

## 3. 设计原则

### 3.1 DECIMAL精度设计

**精度选择原则**：
- 预算字段用2位小数：最终对账用，精确到分（人民币最小单位）
- 竞价字段用6位小数：内部计算用，避免累积误差

**字段精度**：

| 表 | 字段 | 类型 | 说明 |
|---|------|------|------|
| rtb_campaign | budget | DECIMAL(12,2) | 总预算，2位小数（分） |
| rtb_campaign | daily_budget | DECIMAL(12,2) | 日预算，2位小数（分） |
| rtb_campaign | budget_used | DECIMAL(12,2) | 已消耗，2位小数（分） |
| rtb_ad | bid_price | DECIMAL(10,6) | 出价，6位小数（精确计算） |
| rtb_bid_log | bid_price | DECIMAL(10,6) | 出价，6位小数 |
| rtb_bid_log | win_price | DECIMAL(10,6) | 赢价，6位小数 |
| rtb_bid_log | cost | DECIMAL(10,6) | 花费，6位小数 |

**为什么用6位小数？**

1. **避免累积误差**：
   ```
   场景：日展示1000万次，单次0.051234元

   2位精度累计：0.05 × 10,000,000 = 500,000元
   6位精度累计：0.051234 × 10,000,000 = 512,340元
   差异：12,340元/天，年差异约450万元
   ```

2. **存储空间相同**：
   ```
   DECIMAL(10,2) = 5字节（NOT NULL）
   DECIMAL(10,6) = 5字节（NOT NULL）
   精度更高，空间相同
   ```

3. **符合财务分摊原则**：
   - 广告计费本质是财务分摊
   - 每次展示的花费 = CPM / 1000
   - 保留高精度避免分摊误差累积

4. **范围足够**：
   ```
   DECIMAL(10,6): 范围 ±9999.999999元
   覆盖正常CPM价格区间：0.5 - 5000元/千次
   ```

### 3.2 简洁性

**不加冗余表**：
- ❌ 不加 rtb_campaign_cost（日汇总表）
- ❌ 不加 rtb_bid_log_hourly（小时汇总表）
- ✅ rtb_bid_log + 索引 = 足够快

**原因**：
- 有索引（campaign_id, request_time），查询足够快
- MVP阶段数据量小，无需预聚合
- 后期需要再加，遵循YAGNI原则

### 3.3 长期性

**表结构稳定**：
- Campaign、Ad、Bid_log 三张表是核心
- 后续扩展通过加字段、加索引，不改表结构

**可扩展**：
- 需要报表时，再加汇总表
- 需要分析时，加数据分析模块
- 基础表不变

### 3.4 预算显示设计

**设计原则**：
- 准确值来源：rtb_bid_log的SUM(cost)，status=2（赢了）
- budget_used字段：仅作缓存，不保证实时性
- 显示时实时统计，而不是读取缓存

**为什么这样设计？**
1. **避免频繁更新**：每次竞价赢了都更新budget_used会导致数据库压力大
2. **数据准确**：bid_log是完整的竞价记录，统计结果绝对准确
3. **灵活性强**：支持实时刷新、自动刷新、手动刷新

**性能考虑**：
```
SELECT SUM(cost) FROM rtb_bid_log
WHERE campaign_id = ? AND status = 2

使用索引 idx_campaign_time，查询速度快
MVP阶段数据量小，统计性能足够
后期数据量大时可优化（如定期汇总）
```

### 3.5 性能保证

**索引策略**：
```sql
-- 竞价日志：按活动+时间查询
KEY `idx_campaign_time` (`campaign_id`, `request_time`)

-- 广告：按活动+状态查询
KEY `idx_campaign_status` (`campaign_id`, `status`)

-- 活动：按广告主+状态查询
KEY `idx_advertiser_status` (`advertiser_id`, `status`)

-- 删除历史数据：按时间查询
KEY `idx_request_time` (`request_time`)
```

**数据清理**：
- 定期删除90天前的数据
- 使用`idx_request_time`索引，删除快
- 后期数据量大了再加分区

## 4. 业务逻辑

### 4.1 状态管理

**状态定义**：

| 状态值 | 名称 | 说明 |
|--------|------|------|
| 0 | 草稿 | 创建后默认状态，未完成配置 |
| 1 | 进行中 | 正在投放中，会参与竞价 |
| 2 | 暂停 | 暂时停止投放，可恢复 |
| 3 | 已完成 | 结束时间到了，或预算用完 |
| 4 | 已取消 | 手动取消，不再投放 |

**状态流转**：
```
                    创建Campaign
                         ↓
                    ┌─────────┐
                    │  草稿(0) │
                    └────┬────┘
                         │ 启动
                         ↓
                    ┌─────────┐
    暂停 ───────────→│进行中(1)│←────────── 恢复
    (手动)           └────┬────┘          (手动)
                         │
           ┌─────────────┴─────────────┐
           │             │             │
       预算用完      结束时间到      手动暂停
      (竞价时检查)  (竞价/页面检查)   (手动)
           │             │             │
           ↓             ↓             ↓
    ┌────────────────────────────────┐
    │           已完成(3)             │
    └────────────────────────────────┘
                                      ↑
                                 手动取消
                                   (手动)
                                      ↓
                              ┌──────────┐
                              │已取消(4) │
                              └──────────┘
```

**状态更新机制**（按需更新，无定时任务）：

```java
/**
 * 统一的状态更新方法
 * 在两个地方调用：
 * 1. 竞价时（canBid方法）
 * 2. 页面访问时（getById方法）
 */
private void updateStatusIfNeeded(Campaign campaign) {
    LocalDateTime now = LocalDateTime.now();

    // 只有进行中(1)或暂停(2)才需要检查
    if (campaign.getStatus() != 1 && campaign.getStatus() != 2) {
        return;
    }

    // 1. 时间过期检查 → 已完成
    if (now.isAfter(campaign.getEndTime())) {
        campaign.setStatus(3);
        campaignMapper.updateById(campaign);
        return;
    }

    // 2. 预算用完检查 → 已完成
    BigDecimal used = getBudgetUsedFromRedis(campaign.getId());
    if (used.compareTo(campaign.getBudget()) >= 0) {
        campaign.setStatus(3);
        campaignMapper.updateById(campaign);
    }
}

// 竞价时调用
public boolean canBid(Long campaignId) {
    Campaign campaign = campaignMapper.selectById(campaignId);

    // 先检查并更新状态
    updateStatusIfNeeded(campaign);

    // 只有进行中才能参与竞价
    return campaign.getStatus() == 1;
}

// 页面访问时调用
@GetMapping("/api/campaigns/{id}")
public Result<Campaign> getById(@PathVariable Long id) {
    Campaign campaign = campaignMapper.selectById(id);

    // 访问时也检查并更新状态
    updateStatusIfNeeded(campaign);

    return Result.ok(campaign);
}
```

**优点**：
- ✅ 无定时任务，不浪费资源
- ✅ 按需更新，有访问才检查
- ✅ 实时性好，竞价和查看页面都能看到最新状态
- ✅ 简单高效，符合YAGNI原则

### 4.2 预算控制

**Redis存储累计消耗**：
```java
// 赢了竞价后，累加到Redis
public void onWinNotice(Long campaignId, BigDecimal cost) {
    // 1. 累加到Redis（实时）
    String key = "campaign:budget:" + campaignId;
    redis.incrBy(key, cost);

    // 2. 记录到bid_log（用于对账）
    bidLogMapper.insert(...);
}

// 从Redis获取已消耗
private BigDecimal getBudgetUsedFromRedis(Long campaignId) {
    String key = "campaign:budget:" + campaignId;
    String value = redis.get(key);
    return value != null ? new BigDecimal(value) : BigDecimal.ZERO;
}
```

**竞价时预算检查**：
```java
// 竞价前检查（从Redis读取）
BigDecimal used = getBudgetUsedFromRedis(campaignId);
boolean canBid =
    used.compareTo(campaign.getBudget()) < 0 &&
    used.compareTo(campaign.getDailyBudget()) < 0;
```

**budget_used字段说明**：
- `budget_used`不是实时值，只是一个缓存字段
- 准确的累计消耗：从Redis读取 `campaign:budget:{campaignId}`
- 显示逻辑：页面加载时从Redis读取，而不是读取budget_used字段
- 对账逻辑：从bid_log统计，用于核对

```javascript
async function loadCampaign(id) {
  const campaign = await getCampaign(id);
  // 后端已经从Redis读取了budgetUsed
  return campaign;
}

// 2. 自动刷新（每30秒）

// 3. 手动刷新按钮
<el-button @click="refreshBudgetUsed">实时更新累计消耗</el-button>
```

### 4.4 投放控制

**投放方式定义**：

| 模式 | 值 | 说明 | 适用场景 |
|------|---|------|----------|
| 加速投放 | 1 | 尽快花完预算，不做时间限制 | 短期促销、紧急活动 |
| 均匀投放 | 2 | 按时间均匀分配预算（默认） | 长期品牌广告、日常投放 |

**投放控制逻辑**：

```java
// 竞价时检查
public boolean canBid(Long campaignId) {
    Campaign campaign = campaignMapper.selectById(campaignId);

    // 1. 状态检查
    updateStatusIfNeeded(campaign);
    if (campaign.getStatus() != 1) {
        return false;
    }

    // 2. 预算检查
    BigDecimal used = getBudgetUsedFromRedis(campaignId);
    if (used.compareTo(campaign.getBudget()) >= 0 ||
        used.compareTo(campaign.getDailyBudget()) >= 0) {
        return false;
    }

    // 3. 投放速度检查（均匀投放）
    if (campaign.getDeliveryMode() == 2) {
        return checkDeliveryPace(campaign, used);
    }

    // 加速投放：只要有预算就投
    return true;
}

// 均匀投放：检查是否超进度
private boolean checkDeliveryPace(Campaign campaign, BigDecimal todayUsed) {
    BigDecimal dailyBudget = campaign.getDailyBudget();

    // 计算当前时间占全天的比例
    LocalDateTime now = LocalDateTime.now();
    LocalDateTime dayStart = now.toLocalDate().atStartOfDay();
    long minutesPassed = ChronoUnit.MINUTES.between(dayStart, now);
    double dayProgress = (double) minutesPassed / 1440;  // 一天1440分钟

    // 预期应该花费多少
    BigDecimal expectedSpend = dailyBudget.multiply(new BigDecimal(dayProgress));

    // 如果已花费 > 预期 + 10%容差，说明花快了，暂停投放
    BigDecimal tolerance = expectedSpend.multiply(new BigDecimal("0.1"));
    if (todayUsed.compareTo(expectedSpend.add(tolerance)) > 0) {
        return false;  // 暂停投放
    }

    return true;
}
```

**为什么有10%容差？**
- 避免临界点频繁开关
- 例如：12:00时，预期花50元，实际花了54元（108%），不应该暂停
- 例如：12:00时，预期花50元，实际花了60元（120%），应该暂停

**加速投放示例**：
```
日预算：1000元
当前时间：12:00（已过50%）
已消耗：800元（80%）

→ 继续投放，尽快花完
```

**均匀投放示例**：
```
日预算：1000元
当前时间：12:00（已过50%）
已消耗：800元（80%）
预期消耗：500元

→ 超进度 + 容差 = 550元
→ 800 > 550，暂停投放
→ 等时间进度赶上，恢复投放
```

**实现逻辑**：
```java
// 时段检查
private boolean checkTimeSchedule(Campaign campaign) {
    if (campaign.getScheduleType() == 1) {
        return true;  // 全天投放
    }

    // 获取当前时间
    int dayOfWeek = LocalDateTime.now().getDayOfWeek().getValue();
    LocalTime time = LocalTime.now();
    String timeStr = time.format(DateTimeFormatter.ofPattern("HH:mm"));

    // 解析JSON配置
    ScheduleConfig config = parseScheduleConfig(campaign.getScheduleConfig());

    // 检查是否在允许的时段内
    return config.isInSchedule(dayOfWeek, timeStr);
}
```
