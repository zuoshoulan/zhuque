# 投放活动与广告系统设计文档

## 1. 概述

本系统采用**三层架构**设计投放活动、广告组和广告，符合业界主流广告平台（Google Ads、Facebook Ads、字节跳动）的实践。

### 1.1 架构层级

```
Advertiser (广告主)
  ↓ 1:N
Campaign (投放活动)
  ↓ 1:N
AdGroup (广告组) ⭐ 核心配置层
  ↓ 1:N
Ad (广告)
  ↓ N:1
Creative (创意)
  ↓ 1:N
Material (素材)
```

### 1.2 层级职责

| 层级 | 职责 | 核心字段 | 字段数 |
|------|------|----------|--------|
| **Campaign** | 营销目标 | 营销目标、总预算、总时间 | 15 |
| **AdGroup** | 受众+出价 | 定向、出价策略、日预算、时段 | 30 |
| **Ad** | 创意展示 | 创意ID、链接URL、权重 | 10 |

### 1.3 为什么三层？

#### 1.3.1 业界标准

**主流平台都采用三层架构**：
- Google Ads: Campaign → Ad Group → Ad
- Facebook Ads: Campaign → Ad Set → Ad
- 字节跳动: 计划 → 组 → 创意
- 腾讯广告: 推广计划 → 广告组 → 广告

#### 1.3.2 业务逻辑对应

三层架构与广告投放的本质逻辑完美对应：

```
广告主的三个核心问题：
1. 营销目标是什么？    → Campaign（品牌曝光？效果转化？）
2. 给谁看？           → AdGroup（北京iPhone用户？上海安卓用户？）
3. 看什么？           → Ad（创意A还是创意B？图片还是视频？）
```

#### 1.3.3 核心优势

**优势1：A/B测试更方便**
```
Campaign（双11大促）
└─ AdGroup（北京用户）
    ├─ Ad 1（创意A）权重50
    └─ Ad 2（创意B）权重50  ✅ 同一定向测试不同创意
```

**优势2：预算控制更灵活**
```
Campaign（总预算100万）
├─ AdGroup 1（北京用户）日预算5万  ✅ 独立控制
└─ AdGroup 2（上海用户）日预算3万  ✅ 独立控制
```

**优势3：职责清晰，扩展性强**
- Campaign: 15字段（只管营销目标、总预算、总时间）
- AdGroup: 30字段（定向、出价、日预算、时段、频次）
- Ad: 10字段（只管创意、链接、权重）
- 未来扩展：新功能加到对应层，不会让某个表臃肿

#### 1.3.4 性能分析

**数据规模**（中等规模DSP）：
- 100个广告主 × 10个Campaign = 1000个Campaign
- 1000个Campaign × 5个AdGroup = 5000个AdGroup
- 5000个AdGroup × 3个Ad = 15000个Ad

**内存占用**：
```
Campaign: 1000条 × 200字节 ≈ 200KB
AdGroup: 5000条 × 2KB（JSON定向） ≈ 10MB
Ad: 15000条 × 100字节 ≈ 1.5MB
总计：约 12MB
```

**性能对比**：
- 两层架构：<2ms（1次查询）
- 三层架构：<3ms（2次查询）
- **差距：1ms，在100ms RTB超时内可忽略**

**结论**：三层架构的1ms性能损耗换来的是**业务逻辑清晰、扩展性强、维护成本低**，完全值得。

## 2. 数据库设计

### 2.1 rtb_campaign（投放活动表）- 15字段

```sql
CREATE TABLE `rtb_campaign` (
  -- 主键
  `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',

  -- 归属

  `lifetime_budget_used` DECIMAL(15,2) NOT NULL DEFAULT 0 COMMENT '累计已消耗（元）',

  -- 总体时间（Campaign独有）

  -- 状态

  -- 审计字段

  `update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `create_by` VARCHAR(64) COMMENT '创建人',
  `update_by` VARCHAR(64) COMMENT '更新人',
  `deleted` TINYINT NOT NULL DEFAULT 0,

  UNIQUE KEY `uk_campaign_id` (`campaign_id`),
```

## 3. 设计原则

### 3.1 DECIMAL精度设计

**精度选择原则**：
- 预算字段用2位小数：最终对账用，精确到分（人民币最小单位）
- 竞价字段用6位小数：内部计算用，避免累积误差

**字段精度**：

| 表 | 字段 | 类型 | 说明 |
|---|------|------|------|
| rtb_campaign | lifetime_budget | DECIMAL(15,2) | 总预算，2位小数（分） |
| rtb_campaign | lifetime_budget_used | DECIMAL(15,2) | 已消耗，2位小数（分） |
| rtb_ad_group | daily_budget | DECIMAL(12,2) | 日预算，2位小数（分） |
| rtb_ad_group | daily_budget_used | DECIMAL(12,2) | 今日已消耗，2位小数（分） |
| rtb_ad_group | base_bid_price | DECIMAL(10,6) | 基础出价，6位小数（精确计算） |
| rtb_bid_log | bid_price | DECIMAL(10,6) | 出价，6位小数 |
| rtb_bid_log | win_price | DECIMAL(10,6) | 赢价，6位小数 |
| rtb_bid_log | cost | DECIMAL(10,6) | 花费，6位小数 |

**为什么用6位小数？**

1. **避免累积误差**：
   ```
   场景：日展示1000万次，单次0.051234元

   2位精度累计：0.05 × 10,000,000 = 500,000元
   6位精度累计：0.051234 × 10,000,000 = 512,340元
   差异：12,340元/天，年差异约450万元
   ```

2. **存储空间相同**：
   ```
   DECIMAL(10,2) = 5字节（NOT NULL）
   DECIMAL(10,6) = 5字节（NOT NULL）
   精度更高，空间相同
   ```

3. **符合财务分摊原则**：
   - 广告计费本质是财务分摊
   - 每次展示的花费 = CPM / 1000
   - 保留高精度避免分摊误差累积

4. **范围足够**：
   ```
   DECIMAL(10,6): 范围 ±9999.999999元
   覆盖正常CPM价格区间：0.5 - 5000元/千次
   ```

### 3.2 简洁性

**不加冗余表**：
- ❌ 不加 rtb_campaign_cost（日汇总表）
- ❌ 不加 rtb_bid_log_hourly（小时汇总表）
- ✅ rtb_bid_log + 索引 = 足够快

**原因**：
- 有索引（campaign_id, request_time），查询足够快
- MVP阶段数据量小，无需预聚合
- 后期需要再加，遵循YAGNI原则

### 3.3 长期性

**表结构稳定**：
- Campaign、Ad、Bid_log 三张表是核心
- 后续扩展通过加字段、加索引，不改表结构

**可扩展**：
- 需要报表时，再加汇总表
- 需要分析时，加数据分析模块
- 基础表不变

### 3.4 预算显示设计

**设计原则**：
- 准确值来源：rtb_bid_log的SUM(cost)，status=2（赢了）
- budget_used字段：仅作缓存，不保证实时性
- 显示时实时统计，而不是读取缓存

**为什么这样设计？**
1. **避免频繁更新**：每次竞价赢了都更新budget_used会导致数据库压力大
2. **数据准确**：bid_log是完整的竞价记录，统计结果绝对准确
3. **灵活性强**：支持实时刷新、自动刷新、手动刷新

**性能考虑**：
```
SELECT SUM(cost) FROM rtb_bid_log
WHERE campaign_id = ? AND status = 2

使用索引 idx_campaign_time，查询速度快
MVP阶段数据量小，统计性能足够
后期数据量大时可优化（如定期汇总）
```

### 3.5 性能保证

**索引策略**：
```sql
-- 竞价日志：按活动+时间查询
KEY `idx_campaign_time` (`campaign_id`, `request_time`)

-- 广告：按活动+状态查询
KEY `idx_campaign_status` (`campaign_id`, `status`)

-- 活动：按广告主+状态查询
KEY `idx_advertiser_status` (`advertiser_id`, `status`)

-- 删除历史数据：按时间查询
KEY `idx_request_time` (`request_time`)
```

**数据清理**：
- 定期删除90天前的数据
- 使用`idx_request_time`索引，删除快
- 后期数据量大了再加分区

## 4. 业务逻辑

### 4.1 状态管理

**状态定义**：

| 状态值 | 名称 | 说明 |
|--------|------|------|
| 0 | 草稿 | 创建后默认状态，未完成配置 |
| 1 | 进行中 | 正在投放中，会参与竞价 |
| 2 | 暂停 | 暂时停止投放，可恢复 |
| 3 | 已完成 | 结束时间到了，或预算用完 |
| 4 | 已取消 | 手动取消，不再投放 |

**状态流转**：
```
                    创建Campaign
                         ↓
                    ┌─────────┐
                    │  草稿(0) │
                    └────┬────┘
                         │ 启动
                         ↓
                    ┌─────────┐
    暂停 ───────────→│进行中(1)│←────────── 恢复
    (手动)           └────┬────┘          (手动)
                         │
           ┌─────────────┴─────────────┐
           │             │             │
       预算用完      结束时间到      手动暂停
      (竞价时检查)  (竞价/页面检查)   (手动)
           │             │             │
           ↓             ↓             ↓
    ┌────────────────────────────────┐
    │           已完成(3)             │
    └────────────────────────────────┘
                                      ↑
                                 手动取消
                                   (手动)
                                      ↓
                              ┌──────────┐
                              │已取消(4) │
                              └──────────┘
```

**状态更新机制**（按需更新，无定时任务）：

```java
/**
 * 统一的状态更新方法
 * 在两个地方调用：
 * 1. 竞价时（canBid方法）
 * 2. 页面访问时（getById方法）
 */
private void updateStatusIfNeeded(Campaign campaign) {
    LocalDateTime now = LocalDateTime.now();

    // 只有进行中(1)或暂停(2)才需要检查
    if (campaign.getStatus() != 1 && campaign.getStatus() != 2) {
        return;
    }

    // 1. 时间过期检查 → 已完成
    if (now.isAfter(campaign.getEndTime())) {
        campaign.setStatus(3);
        campaignMapper.updateById(campaign);
        return;
    }

    // 2. 预算用完检查 → 已完成
    BigDecimal used = getBudgetUsedFromRedis(campaign.getId());
    if (used.compareTo(campaign.getBudget()) >= 0) {
        campaign.setStatus(3);
        campaignMapper.updateById(campaign);
    }
}

// 竞价时调用
public boolean canBid(Long campaignId) {
    Campaign campaign = campaignMapper.selectById(campaignId);

    // 先检查并更新状态
    updateStatusIfNeeded(campaign);

    // 只有进行中才能参与竞价
    return campaign.getStatus() == 1;
}

// 页面访问时调用
@GetMapping("/api/campaigns/{id}")
public Result<Campaign> getById(@PathVariable Long id) {
    Campaign campaign = campaignMapper.selectById(id);

    // 访问时也检查并更新状态
    updateStatusIfNeeded(campaign);

    return Result.ok(campaign);
}
```

**优点**：
- ✅ 无定时任务，不浪费资源
- ✅ 按需更新，有访问才检查

```java
// 从Redis获取已消耗
private BigDecimal getBudgetUsedFromRedis(Long campaignId) {
    String key = "campaign:budget:" + campaignId;
    String value = redis.get(key);
    return value != null ? new BigDecimal(value) : BigDecimal.ZERO;
}
```

### 4.4 投放控制

**投放方式定义**：

| 模式 | 值 | 说明 | 适用场景 |
|------|---|------|----------|
| 加速投放 | 1 | 尽快花完预算，不做时间限制 | 短期促销、紧急活动 |
| 均匀投放 | 2 | 按时间均匀分配预算（默认） | 长期品牌广告、日常投放 |

**投放控制逻辑**：

```java
// 竞价时检查
public boolean canBid(Long campaignId) {
    Campaign campaign = campaignMapper.selectById(campaignId);

    // 1. 状态检查
    updateStatusIfNeeded(campaign);
    if (campaign.getStatus() != 1) {
        return false;
    }

    // 2. 预算检查
    BigDecimal used = getBudgetUsedFromRedis(campaignId);
    if (used.compareTo(campaign.getBudget()) >= 0 ||
        used.compareTo(campaign.getDailyBudget()) >= 0) {
        return false;
    }

    // 3. 投放速度检查（均匀投放）
    if (campaign.getDeliveryMode() == 2) {
        return checkDeliveryPace(campaign, used);
    }

    // 加速投放：只要有预算就投
    return true;
}

// 均匀投放：检查是否超进度
private boolean checkDeliveryPace(Campaign campaign, BigDecimal todayUsed) {
    BigDecimal dailyBudget = campaign.getDailyBudget();

    // 计算当前时间占全天的比例
    LocalDateTime now = LocalDateTime.now();
    LocalDateTime dayStart = now.toLocalDate().atStartOfDay();
    long minutesPassed = ChronoUnit.MINUTES.between(dayStart, now);
    double dayProgress = (double) minutesPassed / 1440;  // 一天1440分钟

    // 预期应该花费多少
    BigDecimal expectedSpend = dailyBudget.multiply(new BigDecimal(dayProgress));

    // 如果已花费 > 预期 + 10%容差，说明花快了，暂停投放
    BigDecimal tolerance = expectedSpend.multiply(new BigDecimal("0.1"));
    if (todayUsed.compareTo(expectedSpend.add(tolerance)) > 0) {
        return false;  // 暂停投放
    }

    return true;
}
```

**为什么有10%容差？**
- 避免临界点频繁开关
- 例如：12:00时，预期花50元，实际花了54元（108%），不应该暂停
- 例如：12:00时，预期花50元，实际花了60元（120%），应该暂停

**加速投放示例**：
```
日预算：1000元
当前时间：12:00（已过50%）
已消耗：800元（80%）

→ 继续投放，尽快花完
```

**均匀投放示例**：
```
日预算：1000元
当前时间：12:00（已过50%）
已消耗：800元（80%）
预期消耗：500元

→ 超进度 + 容差 = 550元
→ 800 > 550，暂停投放
→ 等时间进度赶上，恢复投放
```

### 4.5 竞价流程

**完整流程**：

```
BidRequest 到达（例：北京 + iOS + iPhone 用户）
  ↓
1. 查询匹配的 Campaign
   - 检查：状态=进行中、时间范围内、有剩余预算
   - 结果：通常匹配 1 个 Campaign
  ↓
2. 查询匹配的所有 AdGroup
   - 检查：定向条件（地域、设备、OS、时段等）
   - 结果：可能匹配多个 AdGroup
   - 示例：
     • AdGroup A: 北京用户    出价2.5元
     • AdGroup B: iOS用户      出价2.0元
  ↓
3. 每个 AdGroup 按权重选择一个 Ad
   - 同一 AdGroup 内有多个 Ad 时，按 weight 权重随机选择
   - 示例：
     • AdGroup A → Ad A1 (权重选中)
     • AdGroup B → Ad B1 (权重选中)
  ↓
4. 计算每个候选 Ad 的最终出价
   - 最终出价 = 基础出价 × 出价调整系数
   - 示例：
     • Ad A1: 2.5 × 1.3(北京调整) = 3.25元
     • Ad B1: 2.0 × 1.2(iOS调整) = 2.40元
  ↓
5. 选择出价最高的 Ad（同广告主内部优选）
   - 目的：避免自己和自己竞价
   - 结果：选出 Ad A1（出价 3.25元）
  ↓
6. 用选中的 Ad 参与 RTB 竞价
   - 返回 BidResponse（只包含这一个 Ad）
   - 如果赢，记录到 rtb_bid_log
  ↓
7. 更新预算消耗（Redis）
```

**关键说明**：

| 层级 | 匹配数量 | 选择逻辑 |
|------|----------|----------|
| Campaign | 通常 1 个 | 按预算/时间/状态筛选 |
| AdGroup | 可能多个 | 按定向条件筛选 |
| Ad（同Group内） | 可能多个 | **按权重随机选** |
| 最终返回 | **只有 1 个** | 选出价最高的那一个 |

**为什么只返回一个 Ad？**

OpenRTB 协议规定：一个 BidResponse 对每个 imp（展示位）只能返回一个 bid。

```json
// BidResponse 示例
{
  "id": "12345",
  "seatbid": [{
    "bid": [{
      "id": "b1",
      "impid": "1",
      "price": 3.25,      // 最终出价
      "adid": "ad_001",
      "crid": "cr_001"
    }]
    // ❌ 不能有第二个 bid 给同一个 imp
  }]
}
```

**代码示例**：

```java
public Ad selectBestAd(BidRequest request, Campaign campaign) {
    // 1. 找所有匹配的 AdGroup
    List<AdGroup> matchedGroups = findMatchingAdGroups(campaign, request);

    // 2. 每个 AdGroup 按权重选 Ad，计算出价
    List<CandidateAd> candidates = new ArrayList<>();
    for (AdGroup group : matchedGroups) {
        // 按权重随机选一个 Ad
        Ad ad = selectAdByWeight(group);
        // 计算最终出价（含调整系数）
        BigDecimal bid = calculateBid(group, ad, request);
        candidates.add(new CandidateAd(ad, bid, group));
    }

    // 3. 选出价最高的
    return candidates.stream()
        .max(Comparator.comparing(CandidateAd::getBid))
        .map(CandidateAd::getAd)
        .orElse(null);
}

// 按权重选 Ad（同 Group 内）
private Ad selectAdByWeight(AdGroup group) {
    List<Ad> activeAds = group.getAds().stream()
        .filter(ad -> ad.getStatus() == 1) // 启用状态
        .collect(Collectors.toList());

    if (activeAds.isEmpty()) return null;

    // 按权重随机选择
    int totalWeight = activeAds.stream()
        .mapToInt(Ad::getWeight)
        .sum();

    int random = ThreadLocalRandom.current().nextInt(totalWeight);
    int cursor = 0;
    for (Ad ad : activeAds) {
        cursor += ad.getWeight();
        if (random < cursor) return ad;
    }
    return activeAds.get(0);
}

// 计算最终出价
private BigDecimal calculateBid(AdGroup group, Ad ad, BidRequest request) {
    BigDecimal baseBid = group.getBaseBidPrice();

    // 应用出价调整系数
    BidAdjustment adj = parseBidAdjustment(group.getBidAdjustments());

    // 设备调整
    String device = request.getDevice().getDevicetype();
    BigDecimal deviceFactor = adj.getDeviceFactor(device); // e.g. mobile: 1.2

    // 地域调整
    String geo = request.getDevice().getGeo().getCountry();
    BigDecimal geoFactor = adj.getGeoFactor(geo); // e.g. CN-11: 1.3

    return baseBid.multiply(deviceFactor).multiply(geoFactor)
        .setScale(6, RoundingMode.HALF_UP);
}
```

```java
private boolean checkTimeSchedule(Campaign campaign) {
```
