# 投放活动与广告系统设计文档

## 1. 概述

本系统采用**两层架构**设计投放活动和广告，符合OpenRTB DSP系统的业界实践。

### 1.1 架构层级

```
Campaign (投放活动)
  ↓ 1:N
Ad (广告)
  ↓ N:1
Creative (创意)
  ↓ 1:N
Material (素材)
```

### 1.2 层级职责

| 层级 | 职责 | 核心字段 |
|------|------|----------|
| Campaign | 钱包 | 预算、时间、状态 |
| Ad | 策略 | 出价、定向、创意关联 |
| Creative | 内容 | 落地页、展示URL |
| Material | 文件 | 图片、视频等素材 |

### 1.3 为什么两层？

**业界实践**：
- Beeswax、RTB4FREE等开源DSP均为两层
- Google/Facebook广告平台用三层，但那是搜索/社交广告，不是DSP

**DSP特点**：
- 实时竞价要求毫秒级响应
- Ad是完整竞价单元
- 减少层级 = 提升查询效率

## 2. 数据库设计

### 2.1 rtb_campaign（投放活动表）

```sql
CREATE TABLE `rtb_campaign` (
  -- 主键
  `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `campaign_id` VARCHAR(64) NOT NULL COMMENT '投放活动ID',

  -- 归属
  `advertiser_id` BIGINT NOT NULL COMMENT '广告主ID（sys_user.id）',

  -- 基础信息
  `name` VARCHAR(255) NOT NULL COMMENT '活动名称',
  `description` TEXT COMMENT '活动描述',

  -- 预算设置
  `budget` DECIMAL(12,2) NOT NULL COMMENT '总预算（元），必须设置',
  `daily_budget` DECIMAL(12,2) NOT NULL COMMENT '日预算（元），必须设置',
  `budget_used` DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '累计已消耗（元），缓存字段，准确值从bid_log统计',

  -- 时间设置
  `start_time` DATETIME NOT NULL COMMENT '开始时间',
  `end_time` DATETIME NOT NULL COMMENT '结束时间',

  -- 状态
  `status` TINYINT NOT NULL DEFAULT 0 COMMENT '状态：0=草稿/1=进行中/2=暂停/3=已完成/4=已取消',

  -- 投放设置
  `delivery_mode` TINYINT DEFAULT 1 COMMENT '投放方式：1=加速投放/2=均匀投放/3=手动投放',

  -- 审计字段
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `deleted` TINYINT NOT NULL DEFAULT 0,

  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_campaign_id` (`campaign_id`),
  KEY `idx_advertiser_status` (`advertiser_id`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='投放活动表';
```

CREATE TABLE `rtb_ad` (

### 2.3 rtb_bid_log（竞价日志表）

**必须有的表**：记录每次竞价，用于对账、排查、分析。

```sql
CREATE TABLE `rtb_bid_log` (
  `id` BIGINT NOT NULL AUTO_INCREMENT,
  `campaign_id` BIGINT NOT NULL COMMENT '活动ID',
  `ad_id` BIGINT NOT NULL COMMENT '广告ID',
  `imp_id` VARCHAR(64) NOT NULL COMMENT '曝光ID（OpenRTB imp.id）',
  `bid_price` DECIMAL(10,6) NOT NULL COMMENT '出价（元）',
  `win_price` DECIMAL(10,6) DEFAULT NULL COMMENT '赢价（元），NULL表示未赢',
  `cost` DECIMAL(10,6) NOT NULL DEFAULT 0 COMMENT '花费（元）',
  `status` TINYINT NOT NULL COMMENT '1=参与/2=赢/3=输',
  `request_time` DATETIME NOT NULL COMMENT '竞价请求时间',
  `response_ms` INT DEFAULT NULL COMMENT '响应耗时（毫秒）',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

  PRIMARY KEY (`id`),
  KEY `idx_campaign_time` (`campaign_id`, `request_time`),
  KEY `idx_ad_time` (`ad_id`, `request_time`),
  KEY `idx_imp_id` (`imp_id`),
  KEY `idx_request_time` (`request_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='竞价日志表';
```

**为什么必须记录每次竞价？**
1. **对账**：广告主核对花费
2. **排查**：为什么没展示？为什么输了？
3. **分析**：赢率、响应时间、效果分析
4. **合规**：审计要求

**数据保留**：
- 定期删除90天前的数据：`DELETE FROM rtb_bid_log WHERE request_time < DATE_SUB(NOW(), INTERVAL 90 DAY)`
- 后期数据量大了再加分区

## 3. 设计原则

### 3.1 DECIMAL精度设计

**精度选择原则**：
- 预算字段用2位小数：最终对账用，精确到分（人民币最小单位）
- 竞价字段用6位小数：内部计算用，避免累积误差

**字段精度**：

| 表 | 字段 | 类型 | 说明 |
|---|------|------|------|
| rtb_campaign | budget | DECIMAL(12,2) | 总预算，2位小数（分） |
| rtb_campaign | daily_budget | DECIMAL(12,2) | 日预算，2位小数（分） |
| rtb_campaign | budget_used | DECIMAL(12,2) | 已消耗，2位小数（分） |
| rtb_ad | bid_price | DECIMAL(10,6) | 出价，6位小数（精确计算） |
| rtb_bid_log | bid_price | DECIMAL(10,6) | 出价，6位小数 |
| rtb_bid_log | win_price | DECIMAL(10,6) | 赢价，6位小数 |
| rtb_bid_log | cost | DECIMAL(10,6) | 花费，6位小数 |

**为什么用6位小数？**

1. **避免累积误差**：
   ```
   场景：日展示1000万次，单次0.051234元

   2位精度累计：0.05 × 10,000,000 = 500,000元
   6位精度累计：0.051234 × 10,000,000 = 512,340元
   差异：12,340元/天，年差异约450万元
   ```

2. **存储空间相同**：
   ```
   DECIMAL(10,2) = 5字节（NOT NULL）
   DECIMAL(10,6) = 5字节（NOT NULL）
   精度更高，空间相同
   ```

3. **符合财务分摊原则**：
   - 广告计费本质是财务分摊
   - 每次展示的花费 = CPM / 1000
   - 保留高精度避免分摊误差累积

4. **范围足够**：
   ```
   DECIMAL(10,6): 范围 ±9999.999999元
   覆盖正常CPM价格区间：0.5 - 5000元/千次
   ```

### 3.2 简洁性

**不加冗余表**：
- ❌ 不加 rtb_campaign_cost（日汇总表）
- ❌ 不加 rtb_bid_log_hourly（小时汇总表）
- ✅ rtb_bid_log + 索引 = 足够快

**原因**：
- 有索引（campaign_id, request_time），查询足够快
- MVP阶段数据量小，无需预聚合
- 后期需要再加，遵循YAGNI原则

### 3.3 长期性

**表结构稳定**：
- Campaign、Ad、Bid_log 三张表是核心
- 后续扩展通过加字段、加索引，不改表结构

**可扩展**：
- 需要报表时，再加汇总表
- 需要分析时，加数据分析模块
- 基础表不变

### 3.4 预算显示设计

**设计原则**：
- 准确值来源：rtb_bid_log的SUM(cost)，status=2（赢了）
- budget_used字段：仅作缓存，不保证实时性
- 显示时实时统计，而不是读取缓存

**为什么这样设计？**
1. **避免频繁更新**：每次竞价赢了都更新budget_used会导致数据库压力大
2. **数据准确**：bid_log是完整的竞价记录，统计结果绝对准确
3. **灵活性强**：支持实时刷新、自动刷新、手动刷新

**性能考虑**：
```
SELECT SUM(cost) FROM rtb_bid_log
WHERE campaign_id = ? AND status = 2

使用索引 idx_campaign_time，查询速度快
MVP阶段数据量小，统计性能足够
后期数据量大时可优化（如定期汇总）
```

### 3.5 性能保证

**索引策略**：
```sql
-- 竞价日志：按活动+时间查询
KEY `idx_campaign_time` (`campaign_id`, `request_time`)

-- 广告：按活动+状态查询
KEY `idx_campaign_status` (`campaign_id`, `status`)

-- 活动：按广告主+状态查询
KEY `idx_advertiser_status` (`advertiser_id`, `status`)

-- 删除历史数据：按时间查询
KEY `idx_request_time` (`request_time`)
```

**数据清理**：
- 定期删除90天前的数据
- 使用`idx_request_time`索引，删除快
- 后期数据量大了再加分区

## 4. 业务逻辑

### 4.1 状态流转

```
Campaign状态：
草稿(0) → 进行中(1) → 暂停(2) → 进行中(1)
   ↓           ↓
已取消(4)   已完成(3)

启动检查：
- 预算 > 0
- 开始时间 < 当前 < 结束时间
- 至少有1个启用的Ad
```

### 4.2 预算控制

**预算检查**：
```java
// 竞价前检查（从bid_log实时统计今日消耗）
BigDecimal todayCost = bidLogMapper.sumCostToday(campaignId);
boolean canBid =
    todayCost < campaign.getDailyBudget() &&
    todayCost < campaign.getBudget();
```

**budget_used字段说明**：
- `budget_used`不是实时值，只是一个缓存字段
- 准确的累计消耗：`SELECT SUM(cost) FROM rtb_bid_log WHERE campaign_id = ? AND status = 2`
- 显示逻辑：页面加载时实时统计bid_log，而不是读取budget_used

**前端显示方案**：
```javascript
// 1. 页面加载时实时统计
async function loadCampaign(id) {
  const campaign = await getCampaign(id);
  const realTimeUsed = await sumBidLogCost(id);  // 实时统计
  return { ...campaign, budgetUsed: realTimeUsed };
}

// 2. 自动刷新（每30秒）
setInterval(() => refreshBudgetUsed(), 30000);

// 3. 手动刷新按钮
<el-button @click="refreshBudgetUsed">实时更新累计消耗</el-button>
```

### 4.3 时间控制

**当前设计（MVP阶段）**：
```java
// 只检查日期范围
boolean canBid =
    now.after(campaign.getStartTime()) &&
    now.before(campaign.getEndTime());
```

**后续扩展：时段控制**：
```sql
-- rtb_campaign 表扩展字段
`schedule_type` TINYINT DEFAULT 1 COMMENT '投放时段：1=全天/2=工作日/3=自定义',
`schedule_config` JSON COMMENT '时段配置'
```

**JSON配置示例**：
```json
// 简化版：每天统一的时段
{
  "time_ranges": ["09:00-12:00", "14:00-18:00"]
}

// 完整版：按星期设置
{
  "monday": ["09:00-18:00"],
  "tuesday": ["09:00-18:00"],
  "wednesday": ["09:00-18:00"],
  "thursday": ["09:00-18:00"],
  "friday": ["09:00-18:00"],
  "saturday": ["10:00-22:00"],
  "sunday": ["10:00-22:00"]
}
```

**扩展后的竞价判断**：
```java
boolean canBid =
    checkDateRange(campaign) &&
    checkTimeSchedule(campaign) &&  // 时段检查
    checkBudget(campaign);
```

**业界实践参考**：
- Google Ads: Ad Schedule支持按星期+时段设置
- 百度推广: 24小时分段，可以每小时设置
- 腾讯广告: 自定义时段，支持多个时间段

### 4.4 竞价流程

```
BidRequest到达
  ↓
查询匹配的Campaign（预算、时间、状态）
  ↓
查询匹配的Ad（出价、创意）
  ↓
参与竞价
  ↓
记录到 rtb_bid_log
  ↓
如果赢，更新 budget_used
```

**实现逻辑**：
```java
// 时段检查
private boolean checkTimeSchedule(Campaign campaign) {
    if (campaign.getScheduleType() == 1) {
        return true;  // 全天投放
    }

    // 获取当前时间
    int dayOfWeek = LocalDateTime.now().getDayOfWeek().getValue();
    LocalTime time = LocalTime.now();
    String timeStr = time.format(DateTimeFormatter.ofPattern("HH:mm"));

    // 解析JSON配置
    ScheduleConfig config = parseScheduleConfig(campaign.getScheduleConfig());

    // 检查是否在允许的时段内
    return config.isInSchedule(dayOfWeek, timeStr);
}
```
